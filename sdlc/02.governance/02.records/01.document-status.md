# 03 — Document status **standard**: completeness, cross-checks, and how a status is claimed

**Type:** `standard` · **Requires:** [`03.artifacts.md`](../01.standard/01.artifacts.md) (shape) · [`01.marks.md`](../01.standard/03.gates/01.marks.md) (marks)

> **Why this became a standard.** It used to be a table of numbers. Every number was typed by hand, and **four separate totals were
> wrong in one session** (82 vs 83 AC · 22 vs 23 · "391 tokens" · a BIP totals update that never wrote). A status that is typed is a
> **claim**; a status that is **checked** is a **fact**.
>
> So this file defines: **what "documented" means**, **eight cross-checks** that must pass, and **how results are recorded**.
> The table at the end is an **instance** generated by those checks — never an opinion.

## 0. This file is a **precondition**, not a report

> **Stage 0** ([`01.sdlc-delivery-lifecycle-standard`](../01.standard/03.gates/02.lifecycle.md) §1.1 **P0.3**):
> a project whose SDLC tree has **no `03.document-status.md`** has not started the pipeline. `sdlc:init` must create it
> ([`API-15`](../../07.technical/03.api/01.contracts.md)), and `sdlc:check` must fail without it.

| Why it is a precondition | Consequence of skipping it |
|---|---|
| it is the only place that says what **exists** and what is **missing** | "documented" becomes whoever speaks last |
| the gate instruments **read** it ([§5](#5-process-completeness--this-file-feeds-the-gates-it-does-not-replace-them)) | pre-flight and go/no-go become opinions |
| it records the **cross-check results** | nobody can tell whether a claim was ever checked |

**An SDLC tree without this file is a folder.** The register is what turns *"we wrote documents"* into *"this exists, this is missing,
and this is how we know"*.

## 1. Definition — "documented" means **three** things, not one

| Level | Meaning | Fails when |
|---|---|---|
| **exists** | the file is present | a link to it is broken |
| **conforms** | it has the required header and sections for its `type` | a key or a section is missing |
| **connected** | it is reachable from a requirement and to a test | an `AC` has no `SCN`, a `US` has no `REQ` |

**Only all three count.** A file that exists but is unreachable is **dead weight**; a file that conforms but nothing points at it is
**decoration**.

## 2. The completeness contract — what each item must have

An **item** (capability) is "documented" when every **required** slot is filled. `OUT` is allowed **only with a reason** and counts as
filled.

| Slot | Required | Belongs to |
|---|---|---|
| `REQ` | ✅ always | stage 1 |
| `UC` | ✅ when the item has a user-facing flow | stage 2 |
| `US` | ✅ ≥ 1 | stage 2 |
| `AC` | ✅ ≥ 1 per US | stage 2 |
| **`BRD`** (narrative) | ✅ **một bản cho mỗi `UC`**, hoặc `OUT` — reason | stage 2 |
| **`PRD`** | ✅ một bản cho sản phẩm; **mỗi goal ở vision phải có ≥1 chỉ số** | stage 1 |
| **`FRD`** | ✅ **một file cho mỗi chức năng**; mỗi file đủ 6 mục **và** nêu ≥1 điều kiện từ chối | stage 1 |
| **`SRS`** | ✅ có `REQ` **và** `NFR` đo được (cách đo + ngưỡng) | stage 1 |
| `SCN` | ✅ **every** AC | stage 3 |
| `interface` | ✅, or `OUT` — **reason required** | stage 4 |
| `data` | ✅, or `OUT` — **reason required** | stage 5 |
| **`WBS`** | ✅ — **deliverable tree with every leaf owning `AC`** | stage 6, **before** packets |
| **`BIP`** (backend slice) | ✅, or `OUT` — reason | stage 6 |
| **`FIP`** (frontend slice) | ✅, or `OUT` — reason | stage 6 |
| **AI spec** | ✅ per capability | stage 2 (agent zone) |
| `executed` scenarios | ✅ before `Done` — **not** before `READY` | stage 8 |

**`WBS` comes before both**, because a slice **is** one leaf of it ([`03.bip-fip`](../01.standard/04.workflow/01.bip-fip.md) §0). A packet written against a slice
the tree does not contain is a packet whose id the tree will contradict.

**`BIP` and `FIP` are separate slots.** A slice may be `[be]`, `[fe]`, or mixed; a mixed slice needs **both**
([`03.bip-fip`](../01.standard/04.workflow/01.bip-fip.md)). One packet column cannot describe two sides.

### 2.1 Chuẩn tham chiếu — vì sao thứ tự này không phải ý thích

| Chuẩn | Nói gì | Áp vào đây |
|---|---|---|
| **PMBOK — WBS** | WBS phân rã deliverable → **work package** (cấp thấp nhất); work package là đơn vị giao việc + ước lượng; luật **100%** (không thiếu, không thừa) | **Slice = một leaf work package**; WBS **phải có trước** packet; leaf không có `AC` ⇒ WBS sai |
| **ISO/IEC 12207** | Nhóm quy trình vòng đời: requirements → design/implementation; **không** thiết kế/cài đặt trước khi yêu cầu được baseline | Packet là **implementation planning** ⇒ sau SRS/`AC`; không "vừa code vừa phát hiện yêu cầu" |
| **IEEE 29148** | Yêu cầu phải: cần thiết · không nhập nhằng · **kiểm chứng được** · **trace được** | Mỗi `REQ` trace `F` + `BR`; mỗi `AC` kiểm được; mỗi leaf WBS sở hữu `AC` |
| **Agile — Definition of Ready** | Story/task chỉ vào thực thi khi đạt **DoR**: `AC` rõ + kiểm được + sized + đủ thông tin | Packet §9 `READY` = **DoR ở cấp slice**: `AC` + planes B/C/D + `SCN` **đã khai** (không cần test chạy — `D-81`) |

**Kết luận của cả ba chuẩn:** quyền lực chạy **một chiều**
`REQ → US/AC → WBS (work package) → BIP/FIP (DoR của work package) → SCN → code`.
**Không chuẩn nào** đặt implementation plan trước work breakdown.

### 2.2 Hai thứ tự khác nhau — đừng trộn

| | Thứ tự **thời gian** (cái gì sinh trước) | Thứ tự **quyền lực** (cái gì thắng khi lệch) |
|---|---|---|
| Yêu cầu ↔ thiết kế/thi công | `AC` → WBS → packet → SCN → code | **`AC`/`REQ` thắng**; design không được sửa yêu cầu |
| Packet ↔ WBS | WBS slice có trước, packet sau | **WBS thắng packet** về danh tính slice + scope |
| SCN ↔ code | SCN **viết trước**, **chạy sau** impl | SCN đỏ ⇒ sửa impl, **không** sửa `AC` |

### 2.3 CR pipeline — vòng bổ sung chéo

Vòng lặp **được phép**; **đảo quyền thì không**. Mỗi vòng lặp là **một CR** đi qua CR pipeline (§2.5) rồi quay lại
**đúng bước** bị ảnh hưởng với artifact **version+1**.

**Không có sổ CR riêng.** Dấu vết của một CR là **version bump của artifact bị mở lại**, cộng `D` mới nếu đổi
scope/metric/goal. Không có file log nào phải giữ.

| Phát hiện ở | Mở lại bước | Ai quyết | Artifact đổi | **Cấm** |
|---|---|---|---|---|
| S6–S12 thấy `AC`/`REQ` thiếu hoặc không kiểm được | **S6** (lên S5/S4 nếu `REQ` sai) | BA (+ operator nếu đổi scope) | `AC` version+1 (+ SRS/FRD) | packet tự thêm `AC` |
| S9 thấy slice quá lớn/không giao được (8–80) | **S8** | người giữ WBS | WBS version+1 | packet tự tách slice |
| S8 cần chi tiết kỹ thuật | **không mở bước** — spike timebox | TECH | spike note | spike tạo slice id / `READY` |
| S12 `SCN` đỏ | **S11** (hoặc S9 nếu packet sai) | dev + verify | code / packet | sửa `AC` cho khớp code |
| S8/S9 thiếu plane phải cite | **S7** | TECH/UX | plane B/C/D/UI version+1 | cite file không tồn tại |

**Điều kiện thoát vòng (đủ cả 4 mới vào code):** (1) `AC` kiểm được · (2) leaf có owner + size ·
(3) packet §9 `READY` · (4) `SCN` đã khai.

Sơ đồ: [`05.main-pipeline`](../04.diagrams/01.main-pipeline.md) — **Mermaid là nguồn sự thật**, ảnh là artifact sinh ra.

| Ký hiệu | Nghĩa |

### 2.5 CR pipeline — flow và impact vào pipeline chính

CR pipeline có trạng thái + cổng + người quyết. Nó **không đảo** pipeline chính: chỉ mở lại bước sớm hơn rồi chạy lại
gate xuôi.

#### 2.5.1 Trạng thái và cổng

| Bước | Trạng thái | Cổng (điều kiện qua) | Ai |
|---|---|---|---|
| `C1` | `raised` | có mã CR · trigger hợp lệ · nguồn + ngày + artifact bị ảnh hưởng | người phát hiện |
| `C2` | `triaged` | có owner · phân loại **detail** vs **scope/metric/goal** · không trùng vòng cũ | owner bước nguồn |
| `C3` | `impacted` | liệt kê **artifact đổi · bước mở lại · gate phải chạy lại · SCN/evidence ảnh hưởng** | owner + QA |
| `C4` | `decided` | approve/reject; **đổi scope/metric/goal ⇒ bắt buộc `D` mới + reopen PRD** | BA / WBS owner / TECH / operator |
| `C5` | `applied` | artifact **version+1**; quyền lực **không đảo** (packet không sửa AC, code không sửa SCN) | owner |
| `C6` | `re-verified` | **chạy lại gate downstream** từ bước bị mở lại | QA/verify |
| `C7` | `closed` | downstream xanh · đóng vòng · bài học nếu lặp | Lead |
| — | `rejected` | ghi lý do ở chính artifact/quyết định, **không xoá** | người quyết C4 |

#### 2.5.2 Flow

Sơ đồ: [`06.cr-pipeline`](../04.diagrams/02.cr-pipeline.md) — **Mermaid là nguồn sự thật**, ảnh là artifact sinh ra.

#### 2.5.3 Impact — bước nào bị mở lại, gate nào chạy lại

| Bước bị mở lại | Khi nào | Artifact đổi | Gate chạy lại | Ảnh hưởng tiếp |
|---|---|---|---|---|
| **S7** planes | thiếu/sai thứ packet phải cite | plane version+1 | `G7 → G13` | packet cite bản mới · UI re-check |
| **S8** WBS | slice quá lớn/không giao được | WBS version+1 | `G8 → G13` | packet cho leaf mới · Jira **tách** ticket |
| **S6** US/AC | `AC` thiếu/không kiểm được | `AC` version+1 | `G6 → G13` | leaf đổi chủ `AC` · packet re-open · Jira re-ticket |
| **S5** SRS | `REQ` sai/thiếu | SRS version+1 | `G5 → G13` | PRD/FRD/AC xuôi lại |
| **S4** FRD | hành vi đặc tả sai/thiếu | FRD version+1 | `G4 → G13` | SRS/AC xuôi lại |
| **S9** packet | packet sai/thiếu so với `AC`/plane | packet version+1 | `G9 → G13` | impl/SCN theo packet mới |
| **S11** code | code lệch packet/`SCN` | code | `G11 · G12` | SCN status + evidence cập nhật; **không** sửa `AC` |
| *(spike)* | bất định kỹ thuật | không phải artifact chuẩn | không | chỉ giảm bất định; **không** tạo slice/`READY` |

#### 2.5.4 Ảnh hưởng lên pipeline chính

| Khía cạnh | Ảnh hưởng |
|---|---|
| **Thứ tự** | CR **không** đảo: chỉ mở lại bước sớm hơn rồi chạy gate xuôi. Không có CR nào cho "code trước, AC sau" |
| **Artifact** | Mọi CR áp dụng ⇒ **version bump** artifact bị mở lại; không có sổ CR riêng |
| **Gate** | Gate **từ bước bị mở lại trở xuống** phải chạy lại; gate phía trên chỉ khi CR chạm artifact của nó |
| **DoD / Done** | Còn CR **open** ảnh hưởng slice ⇒ **không** được ký `Done` (`S13 → S14` bị chặn) |
| **Jira** | CR mở ⇒ ticket slice liên quan **blocked/reopened**; tách slice ⇒ tách ticket |
| **WBS / packet** | CR ở S6/S8 có thể đổi chủ `AC`/tách leaf ⇒ packet cũ **hết hiệu lực**, phải viết lại |
| **Chi phí** | CR càng muộn càng đắt (S11+ đắt hơn S5) |

#### 2.5.5 Tín hiệu — bước nào bị mở lại nhiều thì bước đó đang yếu

| Bước mở lại nhiều | Nghĩa là | Siết ở |
|---|---|---|
| S4/S5 | yêu cầu chưa chắc | `G4`/`G5`: đủ mục + trace trước khi qua |
| S6 | `AC` chưa kiểm được | `G6`: AC phải có điều kiện + cách kiểm |
| S7 | plane thiếu | hoàn tất B/C/D **trước** S8 |
| S8 | WBS sizing sai | luật 8–80; tách slice ngay |
| S9 | packet mơ hồ | siết DoR (`§9 READY`) |
| S11 | code lệch packet | siết `G11`/`G12` + packet rõ hợp đồng/test |
