# 30 — Provider routing

## Decision

Provider is selected **per work area**, not as a flat list of providers.

| Area | Options | Default |
|---|---|---|
| Work management | Jira | `.md` |
| Design management | Figma · Penpot | `.md` |
| Content management | Notion · Confluence | `.md` |

No provider selected means:

```text
manage directly in .md files
```

## Why

A flat list mixes unrelated concerns:

```text
Jira       tasks
Figma      design
Notion     documents
```

Selecting one provider globally would force one tool to own all artifact kinds.

## Scope

```text
Knowledge tab → Provider routing
  work     → jira | md
  design   → figma | penpot | md
  content  → notion | confluence | md
```

Config/credentials live in:

```text
/consumers/:id/plugins
```

Enable/configure a provider there; routing only selects it for the area.

## Persistence

```json
{
  "knowledge": {
    "providers": {
      "routing": {
        "work": "jira",
        "design": "md",
        "content": "md"
      }
    }
  }
}
```

Provider config and secret refs remain in `platform.consumer_plugin`.

## Rules

```text
INV-PR1  no provider = .md is valid and is the default
INV-PR2  selecting provider does not enable/configure it
INV-PR3  provider must be enabled + configured in Plugins to be healthy
INV-PR4  one provider per area; no multi-select
INV-PR5  routing does not bypass Stack/Host binding policy
```
