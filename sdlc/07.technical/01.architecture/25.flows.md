# Flows — consumer-level worker flow

## Decision

Flows are a **separate consumer page**, not a Settings tab:

```text
/consumers/:id/flows
```

Reasons:

- flow authoring is a setup step, not a settings field
- canvas needs full viewport
- flow versions are independent of Stack versions

## Model

Canonical files:

```text
.harness/flows/<flowId>.draft.json
.harness/flows/<flowId>.v<N>.json
.harness/flows/index.json       default flow pointer
```

```ts
FlowDefinition {
  id, name, version, status
  nodes: [{ workerId, x, y }]
  edges: [{ id, from, to, on, condition, priority }]
  viewport
}
```

- `draft` is mutable.
- `v<N>` is immutable.
- publish writes a version and removes the draft.
- editing a published flow creates the next draft version.
- publish sets the default pointer only when the flow is already default or no default exists.
- default can be changed explicitly with `PUT /flows/default`.

## SLP proposal

`agents/rules/*slp*.mdc` may contain a fenced JSON block:

````markdown
```slp-flow
{
  "id": "slp-proposal",
  "name": "SLP Proposal",
  "edges": [
    { "from": "worker-scout", "to": "worker-plan", "on": "PASS" }
  ]
}
```
````

The Flows page shows:

```text
SLP flow proposal
agents/rules/core.slp.mdc · 7 nodes · 8 edges
[Create draft]
```

This creates a draft only. Human must validate and publish.
Prose is never parsed as a flow.

## 2D / 3D observability

## Default flow

For `testeso`:

```text
id:    that-tinh-tran
name:  7 Tinh Trận
nodes: 7 workers
edges: 8
version: 1
status: published
```

Workers:

```text
Scout · Plan · Build · Fixbug · Verify · Audit · QC
```

The validation allows intentional loops (`FLOW_HAS_LOOP`) because verify ↔ fixbug
is a repair loop, not a schema error.
