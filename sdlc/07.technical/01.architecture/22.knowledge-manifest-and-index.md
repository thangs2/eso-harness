# 22 — Knowledge manifest, header standard, Postgres index

**Mục đích:** chốt một chuẩn duy nhất cho `header key` + `manifest` + cách Postgres giúp tìm file
relative/linking/ref — thay vì mỗi nơi một kiểu.

**Không thay thế:** [`01.artifacts`](../../02.governance/01.standard/01.artifacts.md),
[`19.graph-storage-engine`](19.graph-storage-engine.md), [`20.manifest`](../02.data-design/20.manifest.md),
[`26.graph-schema`](../02.data-design/26.graph-schema.md).

## 1. Nguyên tắc gốc

```text
File      = content source of truth
Header    = authored contract
Manifest  = machine-readable generated index
Postgres  = derived query index
```

Bốn câu không được trộn:

```text
id       ≠ path
path     ≠ identity
manifest ≠ content
index    ≠ source of truth
```

Nếu DB mất, rebuild từ files + headers. Nếu header sai, DB **không được** đoán để index như đúng.

## 2. Header key — chuẩn

### 2.1 Ba nhóm key

| Nhóm | Trả lời | Ví dụ |
|---|---|---|
| **Identity / shape** | tài liệu là gì | `id` · `type` · `representation` |
| **Provenance / ownership** | ai chịu, từ đâu | `owner` · `source_of_truth` · `human_sot` · `origin` |
| **Lifecycle / readiness** | đang ở đâu | `status` · `kt_state` · `liveness` · `phase` |

### 2.2 Bảng key

| Key | Zone | Required | Nguồn | Nghĩa |
|---|---|---|---|---|
| `id` | HUMAN + AI | ✅ | authored | định danh ổn định; **không đổi khi đổi path** |
| `type` | HUMAN + AI | ✅ | authored | kind đóng; quyết định required sections |
| `status` | HUMAN + AI | ✅ | authored | `DRAFT·OPEN·READY·READY-SPLIT·BLOCKED` |
| `owner` | HUMAN + AI | ✅ | authored | role/team chịu trách nhiệm, không phải người viết |
| `sot_doc_version` | HUMAN + AI | ✅ | authored | version của standard |
| `representation` | HUMAN + AI | ✅ | authored | `human·agent·machine` |
| `source_of_truth` | HUMAN | ✅ | authored | pointer tới canonical source |
| `phase` | HUMAN | ✅ | authored | stage/gate |
| `human_sot` | AI | ✅ | authored | pointer tới HUMAN source |
| `refs` | AI | ✅ khi là capability spec | authored | US/AC id có thật |
| `origin` | manifest | derived/default | type registry | `human·agent·machine` |
| `custodian` | manifest | derived | path/provider | repo · provider · plugin |
| `liveness` | manifest | derived/default | type registry | `frozen·living` |
| `kt_state` | manifest | derived/default | lifecycle | `raw·proposed·approved·retired` |

### 2.3 Hai profile

HUMAN:

```yaml
id: REQ-SET
type: requirements
status: DRAFT
owner: ba
sot_doc_version: "0.1.0"
representation: human
source_of_truth: doc:PRD-ROOT
phase: "3"
```

AI:

```yaml
id: IAM-SPEC
type: capability-spec
status: READY
owner: tech-lead
sot_doc_version: "0.1.0"
representation: agent
human_sot: doc:IAM-HUMAN
refs: [US-IAM-01, AC-IAM-01-01]
```

### 2.4 Pointer syntax

Canonical:

```text
doc:<doc_id>
```

Legacy accepted:

```text
relative/path.md
relative/path.md#section
```

Resolver:

```text
doc:ID       → exact
path.md      → path map → doc_id; unresolved = finding
path.md#a    → doc_id + section id
```

Path chỉ là **locator**, không phải identity.

### 2.5 Key không được đưa vào header

| Không đưa | Vì sao | Ở đâu |
|---|---|---|
| `path` | đổi tên file là gãy identity | manifest/DB |
| `content_hash` | sinh ra | manifest/DB |
| `derived_from` | multi-valued relation | manifest/DB edge |
| `references` | multi-valued relation | manifest/DB edge |
| `supersedes` | relation | manifest/DB edge |
| `external_refs` | relation tới provider | manifest/DB |

Ngoại lệ duy nhất là pointer đơn `source_of_truth` và `human_sot`.

## 3. Manifest — shape chuẩn

```json
{
  "manifest_version": 1,
  "consumer_id": "testeso",
  "root": "/Users/.../test-eso",
  "generated_at": "2026-11-12T00:00:00Z",
  "types": {
    "brd": {
      "required_sections": ["Problem", "Scope", "Rules"],
      "owner": "ba",
      "representation": "human",
      "liveness": "frozen"
    }
  },
  "documents": [
    {
      "doc_id": "DOC-001",
      "path": "sdlc/05.requirements/.../07.harness-settings.md",
      "type": "brd",
      "status": "DRAFT",
      "owner": "ba",
      "representation": "human",
      "content_hash": "sha256:...",
      "facets": {
        "origin": "human",
        "custodian": "repo",
        "liveness": "frozen",
        "kt_state": "raw"
      },
      "source": { "id": "DOC-000", "path": "..." },
      "headings": [{ "id": "s1", "level": 2, "text": "Scope" }],
      "relations": [
        { "kind": "derived_from", "target": "DOC-000", "provenance": "declared" },
        { "kind": "references", "target": "DOC-002", "provenance": "derived" }
      ],
      "external_refs": [
        { "provider": "jira", "id": "ESO-1", "kind": "ticket" }
      ]
    }
  ]
}
```

Rules:

```text
documents[]      one row per file
doc_id           stable; path is locator
facets           derived from type registry or header override
relations        generated from links + pointer keys; provenance recorded
headings         section anchors for relative links
external_refs    provider refs; no content copied
```

## 4. Link & relation model

### 4.1 Link kinds

```text
references        doc mentions doc
derived_from      doc derived from doc
source_of_truth   canonical source pointer
human_sot         AI → HUMAN pointer
supersedes        newer replaces older
owns_kinds        kind ownership relation
mentions_ticket   doc → external ticket
```

### 4.2 Relative link resolution

```text
doc.md
../dir/doc.md
doc.md#heading
doc:ID
provider:id
```

Process:

1. Normalize path relative to document.
2. Reject absolute paths and escapes outside consumer root.
3. Resolve path → doc_id.
4. Resolve anchor → heading id.
5. If unresolved: **finding**, not silent edge.
6. Store raw target + resolved target + provenance.

### 4.3 Edge provenance

Every edge carries:

```text
provenance: declared | derived
source: header | markdown-link | provider
confidence: exact | weak
```

`declared` beats `derived`; conflict is a flag, not deletion.

## 5. Postgres — giúp gì?

### 5.1 Việc DB làm tốt

| Việc | Postgres |
|---|---|
| stable identity / path mapping | PK/FK + unique index |
| direct relations | `graph_edge(from,to,kind)` |
| transitive traversal 1–3 hop | `WITH RECURSIVE` + depth cap |
| reverse impact | index `(to_node_id)` |
| full-text | `tsvector` + GIN |
| exact/prefix search | btree + `pg_trgm` |
| semantic (optional) | `pgvector` on chunks |
| ticket refs | external_ref table |
| provenance | append-only `source_claim` |
| coverage | `manifest_entry` denominator |
| isolation | schema per consumer (D-110) |
| concurrency/rebuild | transaction + index_run |
| drift detection | content_hash + mtime |

### 5.2 Việc DB **không** làm

```text
không sở hữu content
không thay file SoT
không tự sửa header
không tạo edge từ vector similarity
không join cross-consumer
```

## 6. Logical schema (target)

Dùng database `graph` (derived; được phép rebuild). Tên bảng giữ tương thích
[`26.graph-schema`](../02.data-design/26.graph-schema.md) nơi có thể.

```sql
-- identity + catalog
doc_node (
  consumer_id, doc_id, path, type, status, owner,
  representation, content_hash, header_json,
  indexed_at, PRIMARY KEY (consumer_id, doc_id)
);

-- locator: path changes, doc_id doesn't
doc_path (
  consumer_id, doc_id, path, is_current,
  PRIMARY KEY (consumer_id, path, doc_id)
);

-- typed edges
doc_edge (
  consumer_id, edge_id, from_doc_id, to_doc_id, kind,
  conflict boolean, PRIMARY KEY (consumer_id, edge_id)
);

-- raw link attempts, including unresolved
doc_link (
  consumer_id, doc_id, raw_target, resolved_doc_id,
  resolved_anchor, status, provenance
);

-- external provider refs
external_ref (
  consumer_id, doc_id, provider, external_id, kind, url,
  direction, PRIMARY KEY (consumer_id, doc_id, provider, external_id, kind)
);

-- search (derived)
doc_search (
  consumer_id, doc_id, ts tsvector, excerpt text,
  embedding vector(1536), model text
);

-- index runs
doc_index_run (
  consumer_id, build_id, source_hash, status, started_at, finished_at
);
```

If reusing `graph_node`:

```text
graph_node.kind = 'doc'
graph_node.node_key = doc_id
graph_node.path = path (locator, not identity)
```

Then add doc edge kinds or a doc-specific edge table. **Không** trộn code node và doc node nếu
query cần khác nhau; quyết định mở `O-KM4`.

## 7. Query model

### Q1 — direct relatives

```sql
SELECT e.kind, n.doc_id, n.path
FROM doc_edge e JOIN doc_node n ON n.doc_id = e.to_doc_id
WHERE e.from_doc_id = $1;
```

### Q2 — reverse references

```sql
SELECT e.kind, n.doc_id
FROM doc_edge e JOIN doc_node n ON n.doc_id = e.from_doc_id
WHERE e.to_doc_id = $1;
```

### Q3 — transitive 1–3 hop

```sql
WITH RECURSIVE walk(doc_id, depth, path) AS (...)
SELECT ... WHERE depth <= 3;
```

Depth là **hằng số theo câu hỏi**, không phải tham số người dùng.

### Q4 — text search + graph expand

```sql
SELECT doc_id FROM doc_search
WHERE ts @@ websearch_to_tsquery('simple', $1)
ORDER BY ts_rank(...) DESC;
```

Sau đó optional expand 1 hop. **Không** thay graph edge bằng vector.

### Q5 — ticket trace

```sql
SELECT doc_id, provider, external_id, url
FROM external_ref
WHERE provider = 'jira' AND external_id = $1;
```

## 8. Graph hay vector?

| Câu hỏi | Dùng |
|---|---|
| cái này liên quan gì? | **graph edge** |
| vì sao liên quan? | **provenance** |
| tài liệu nào gần nghĩa? | **vector** |
| tìm chính xác id/link? | **relational** |
| ticket nào cover AC? | **external_ref + edge** |
| ai sở hữu kind? | **type registry** |

Quyết định:

```text
Graph = deterministic, provenance, traversal
Vector = probabilistic, semantic, no provenance
```

Không dùng vector để tạo edge. Không dùng graph để trả lời "gần nghĩa".

## 9. Ticket provider

Ticket là **external node**, không phải document content.

```text
provider: jira | linear | github | notion | file
external_id: ESO-1
kind: ticket | story | task | bug | design
```

Rules:

- provider là SoT cho ticket body/status;
- ESO giữ link + id + kind + url;
- ticket → doc edge là `references`/`implements`;
- provider absent ⇒ repo file là SoT;
- sync một chiều; không hai chiều.

## 10. Pipeline index

```text
1. scan files
2. parse header
3. validate header profile
4. assign/resolve doc_id
5. build path map
6. parse relative links + pointer keys
7. parse external refs
8. resolve links → edges + findings
9. derive facets from type registry
10. content_hash + write doc_node/doc_edge/doc_link
11. write index_run
12. run checks
```

Fail closed:

```text
header invalid     → doc invalid, not indexed as healthy
link unresolved    → finding, not silent edge
path escapes root  → finding
duplicate doc_id   → reject index run
```

## 11. Checks

| Check | Kiểm |
|---|---|
| `KM-01` | header profile valid |
| `KM-02` | id unique, not path |
| `KM-03` | path resolves, no escape |
| `KM-04` | relative links resolve |
| `KM-05` | one source of truth per kind |
| `KM-06` | derived ⊆ source |
| `KM-07` | no orphan document |
| `KM-08` | kind has owner |
| `KM-09` | external ref provider known |
| `KM-10` | doc_edge provenance present |

## 12. Migration

```text
Phase 1  header validator + manifest JSON
Phase 2  Postgres doc_node/doc_edge/doc_link
Phase 3  graph traversal + reverse impact
Phase 4  FTS
Phase 5  pgvector optional
Phase 6  external ticket refs
```

Docgraph files:

```text
docgraph index file  → replace by DB index
file scan            → same
relative search      → path map + edge
```
